`proxy.ts`, the stand-in gate:

```ts
import { next } from '@vercel/functions';

export default function proxy(request: Request): Response {
  const want = process.env.TEST_GATE;
  if (!want) return new Response('gate not configured', { status: 503 });
  const header = request.headers.get('x-dh-test');
  const cookie = (request.headers.get('cookie') ?? '').split(/;\s*/).find((c) => c.startsWith('dhtest='))?.slice(7);
  if (header !== want && cookie !== want) return new Response('gate: no test credential', { status: 401, headers: { 'x-gate': 'refused' } });
  return next({ headers: { 'x-gate': 'passed', 'x-gate-host': new URL(request.url).host } });
}
```

`api/file.ts`, the files function. It does not check the credential, on purpose, so any path that skips the gate would show up as a 200:

```ts
import { get } from '@vercel/blob';

export default {
  async fetch(request: Request): Promise<Response> {
    const url = new URL(request.url);
    const path = url.searchParams.get('path');
    if (!path) return new Response('missing path', { status: 400 });
    const t0 = performance.now();
    const result = await get(path, {
      access: 'private',
      ifNoneMatch: request.headers.get('if-none-match') ?? undefined,  // always undefined once deployed: no function receives this header on a GET or HEAD (see below)
      useCache: url.searchParams.get('fresh') !== '1',
    });
    const blobMs = (performance.now() - t0).toFixed(1);            // time to the store's response headers
    const common = { 'cache-control': 'private, no-cache', 'x-fn-region': process.env.VERCEL_REGION ?? '', 'x-blob-ms': blobMs, 'server-timing': `blob;dur=${blobMs}` };
    if (!result) return new Response('not found', { status: 404, headers: common });
    if (result.statusCode === 304) return new Response(null, { status: 304, headers: { ...common, etag: result.blob.etag } });
    return new Response(result.stream, {
      headers: { ...common, 'content-type': result.blob.contentType ?? 'application/octet-stream', etag: result.blob.etag, 'x-content-type-options': 'nosniff' },
    });
  },
};
```

### Vercel's Security Checkpoint (observed, not triggered on purpose)

The 41st `curl` of a sequential burst, in about 7 s, to `dh-learn-studios.vercel.app` got `403` with `x-vercel-mitigated: challenge`, Vercel's Security Checkpoint page. About 15 minutes later it had cleared. A browser-like load of 43 files on one connection was not challenged. The project's firewall overview afterwards (read only) shows no custom rules, Attack Mode off, Bot Protection off, and 7 challenges and 2 denies, all by the rule `sys_dos_mitigation` ("DDoS Mitigation"). The 7 challenges and the one request seen challenged may be one event, counted once per request challenged; that is not known. The denies were most likely this test's own host-mismatch probes, not blocked clients: the probes that sent a TLS name not matching the `Host` got `421 Misdirected Request` (Host and routing, below), and two more such `421` probes later raised the deny count from 2 to 4. A request to a path with an encoded `..` segment got `403` with `x-vercel-mitigated: deny`, so requests refused that way are another likely source of the denies. A third is scanner traffic from third parties: the project's request logs showed a request for `/.env` that this test did not send (it got the gate's `401`), so other parties were probing the project's addresses, and any of their requests the mitigation refused would count too. All three likely, not proven: the overview does not say which requests it counts. The counts in this paragraph (the 41st request, 7 challenges, 2 and then 4 denies) are as read at the time; that output was not saved, and the overview's live counters have since moved.

What Vercel's docs say controls it (`vercel.com/docs/vercel-firewall/ddos-mitigation`): "Vercel provides automatic DDoS mitigation for all deployments, regardless of your plan"; it "uses hundreds of signals and detection factors to fingerprint request patterns … challenging or blocking requests if they appear illegitimate". The page names no threshold. Two escapes exist, both "available on Enterprise and Pro plans", not Hobby: pausing system mitigations for a project for 24 hours, and System Bypass Rules that exempt an IP or CIDR (`vercel.com/docs/vercel-firewall/vercel-waf/system-bypass-rules`, Pro 10 per project, Hobby "N/A"). The challenge "Serves the Vercel Security Checkpoint, which a client passes only by executing JavaScript"; "Real browsers solve it once and continue", while "Scripts, cURL, and Postman can't establish a session" (`vercel.com/kb/guide/suspicious-traffic-in-specific-countries`, written for WAF challenge rules; the system challenge serves the same page).

What it means:

- **A client loading a project**: a curl run that reused one connection for 43 files was not challenged (no browser ran), and a browser passes a challenge if one comes. A `fetch` from a page's own script that gets the challenge sees a `403`, not the page; the hub's client code should treat `403` with `x-vercel-mitigated: challenge` (Vercel asks the browser to prove itself; it cleared on its own) as "reload the page", not as an access error. `x-vercel-mitigated: deny` is different: the request itself was refused (seen for a path with an encoded `..` segment), and it should be reported as a failed request, not retried. That a reload does not clear it rests on that one observation.
- **Automated tests in later slices**: a test that sends many sequential requests from one IP, each on a new connection, can be challenged and then sees `403` for minutes; on Hobby nothing can exempt it. Tests should reuse one connection and pace their requests. The threshold is not known: the one challenge came at the 41st request of one burst, while a sequence of 120 requests, each on a new connection, 105 to the custom domain and 15 to the production alias, met none. That is one observation each way, on two hosts; the docs name no threshold, so a burst under 40 is no guarantee and a longer one is no sure trigger. Tests should read a `403` with `x-vercel-mitigated: challenge` as "throttled by Vercel, wait and retry", and one with `x-vercel-mitigated: deny` as "this request was refused by Vercel", which a retry of the same request is not expected to change (one observation: the path with an encoded `..` segment); neither is a gate result. Do not trigger it on purpose to learn its threshold.

### What the `Files` port needs

Run from this machine with the store's `BLOB_READ_WRITE_TOKEN` in the environment (a script's view, as `share` will run), after `vercel env pull`:

```js
import { put, get, head, list, del } from '@vercel/blob';
await put('c/acme/rebrand/b1/assets/big.bin', body, { access: 'private', contentType: 'application/octet-stream' });
const r = await get('c/acme/rebrand/b1/assets/big.bin', { access: 'private' });        // { statusCode, stream, headers, blob }
const n = await get(path, { access: 'private', ifNoneMatch: etag });                    // usually statusCode 304, stream null; not always (below)
const { blobs, cursor, hasMore } = await list({ prefix: 'c/acme/rebrand/b1/', limit: 1000, cursor });
await del(['c/acme/rebrand/b1/assets/app.js', 'c/acme/other/b1/index.html']);
```

The 2.9.0 SDK also exports `presignUrl` and `issueSignedToken` (listed from the installed package's exports). They are available and were not tested.

The sample files put in the store, named in this section: under `c/acme/rebrand/b1/`, `assets/big.bin` (204,800 random bytes, `application/octet-stream`), `index.html` (a 24-byte HTML page, `text/html; charset=utf-8`) and `assets/app.js` (14 bytes, `text/javascript`); `c/acme/other/b1/index.html` (5 bytes, another project's file); `assets/app.js` and `c/acme/other/b1/index.html` are the two the `del` above removed, so they were listed only before it; and under `c/acme/rebrand/b2/assets/`, 43 files `f0.js` to `f42.js` of random bytes typed `text/javascript`, `f0.js` 204,800 bytes and each of the others 25,600 bytes (so `f8.js` and `f30.js` are 25,600 bytes each). The static file through the gate is the deployment's only static file, its own `index.html`, 80 bytes.

| Op | Worked | What the port must know |
| --- | --- | --- |
| `put(path, body, type)` | yes | `contentType` is kept and comes back on `get`. A put to a path that exists, without `allowOverwrite`, throws `BlobError` "Vercel Blob: This blob already exists, use `allowOverwrite: true` if you want to overwrite it. Or `addRandomSuffix: true` to generate a unique filename." A share writes under a new `<build>`, so it never overwrites; keep the default and treat that error as a bug. The sample project's `dist/` is 43 files (1.1 MB), counted from a build of a scratch copy; all 43 uploaded 8 at a time in 528 ms, and 43 synthetic files (1.3 MB) in 570 ms, each then listed as 43. One 200 KB put alone took 96 to 119 ms (3 tries); an earlier 619 ms was the first call of a fresh script, so it likely includes connection setup. |
| `get(path)` → body, type, etag | yes | `null` for a missing path. Body bytes matched the upload. **The etag differs by encoding:** `put`, `head` and `list` give the strong `"333d…"`; a `get` the store answers with `content-encoding: br` gives the weak `W/"333d…"` and `blob.size` 0; with `accept-encoding: identity` it gives the strong etag and the real size. The echo functions, the web-style one (`api/echo.ts`, and the same file at `api/bare/echo.ts`), its log line left out; the Node ones (`api/echo-node.ts`, `api/bare/echo-node.ts`) read `req.headers` the same way and answer the same body:

```ts

const HIDE = new Set(['cookie', 'x-dh-test', 'authorization']);
export default {

    const names = [...request.headers.keys()].filter((k) => !HIDE.has(k)).sort();
    const values = Object.fromEntries(WATCH.map((h) => [h, request.headers.get(h)]));
```

Three ways were tried to get a 304 inside the function:

- **The gate relays the value under its own header name.** The gate copies `If-None-Match` to `x-dh-inm` in `next({ request: { headers } })`. That header does reach the function, and `get(path, { access: 'private', ifNoneMatch: request.headers.get('x-dh-inm') })` then mostly returns `statusCode: 304, stream: null`. "Mostly" means 119 of 140 tries: in the other 21 the store sent a full `200` with the body although the etag matched. The client got its 304 either way, because the edge made it. As first written the gate set `x-dh-inm` only when `If-None-Match` was present, so a client could send the header itself; the gate must replace it on every request (below).
- **`head` and compare** never read the body, but it adds a store call (median 36 ms, n = 47) and costs one Simple Operation per repeat view (table above), so it is the wrong default on Hobby.
- **Answer from the request alone.** A build's paths are not overwritten while they exist (`c/<client>/<project>/<build>/…`), and if no path ever recurs with different bytes (a build id unique for the life of the store, a requirement for the slice that builds `share`; see the `get` row above), the served ETag can be a pure function of the path, which holds the build id (the one formula is under "What (a) means for the contracts", `Files`). The function then answers a relayed value that matches it weakly (`W/` ignored on both sides) with 304 before calling the store at all, once the checks that guard its 200 have passed (below). Measured: 99 ms median, against 144 ms for the function above, and no store request. The measured run used no etag formula and made no comparison: it was the `mode=none` probe (below), which answers any relayed value with 304 and echoes it back, and the client sent the store's weak etag `W/"333d…"`. So the 99 ms is the cost of a 304 the function makes with no store call; hashing the path and comparing the values were not part of it.

What a repeat view costs without the relay, as built here: one function call, one full store read (on a cache `HIT` no Simple Operation, but the whole body), and a full `200` streamed from the function to the edge, which throws it away. Read against Vercel's private-delivery pricing, that store read and the function's response are what gets billed; the client's empty 304 is not. This is from the docs, not a usage reading. On a cache `MISS` there is also a Simple Operation. The `Files` port's `get` needs no `ifNoneMatch`: the value a client sends is the path's etag, which the store never matches, and even a matching store etag got a store 304 in only 119 of 140 tries. The cheap 304 belongs above the port: the gate relays the value, and the function compares it weakly with the path's etag (the one formula, under "What (a) means for the contracts", `Files`) before any store call.

**The relay header is the client's to set unless the gate replaces it.** The scratch gate first set `x-dh-inm` only when `If-None-Match` was present, so a value the client sent itself went straight through. With the test credential and no `If-None-Match`, `-H 'x-dh-inm: "client-made"'` to `/api/file?path=…&mode=none` got `304` with `etag: "client-made"`. The gate must set or delete the relay header on every request it passes on, whatever the client sent:

```ts
const fwd = new Headers(request.headers);
fwd.delete('x-dh-inm');                                   // never the client's value
const inm = request.headers.get('if-none-match');
if (inm) fwd.set('x-dh-inm', inm);
return next({ headers: { 'x-gate': 'passed' }, request: { headers: fwd } });   // on every request, not only conditional ones
```

After one redeploy of the scratch gate written that way, the same request got `200` with the file and the store's etag, the echo function saw no `x-dh-inm`, and a request sending both `If-None-Match: "real-inm"` and `x-dh-inm: "client-made"` had the relay carry `"real-inm"`. A header left out of `next({ request: { headers } })` does not reach the function. A function the matcher excludes still gets a client's `x-dh-inm` as sent (`/api/bare/echo-node`), so the files function must never sit on an excluded path. The decisive lines, `mode=none`, before and after the fix:

```text
before  client x-dh-inm: "client-made", no If-None-Match        304  etag: "client-made"
after   client x-dh-inm: "client-made", no If-None-Match        200  etag: W/"333d…"
after   If-None-Match: "real-inm" and x-dh-inm: "client-made"   304  etag: "real-inm"
after   /api/bare/echo-node, client x-dh-inm only               function saw x-dh-inm: "client-made"
```

The function treats the relayed value as untrusted input. It can only ever turn the function's own `200` into the function's own `304`: the function runs every check that guards the 200 first (session, host, audience, the path inside the session's client and project), compares the relayed value weakly with the etag of the path it serves (the one formula, under "What (a) means for the contracts", `Files`, computed with no store call) only after all of them pass, and sends that etag on the 304, never the relayed value. A 304 tells the caller that the file exists and that their copy is current, so it needs the same checks as a 200. The scratch `mode=none` checks nothing and echoes the value, which is what made `etag: "client-made"`; it is a probe, not the pattern. With the gate replacing the header, a client can still steer the relay only through its own `If-None-Match`, which is all the relay stands in for, and only for a request that already passed every check. How this sits with S5 ("No function trusts a header the gate set"): the relay carries a cache hint, not identity or permission. The function decides access without it and verifies the session itself; the worst a wrong value can do is turn the caller's own 304 into a 200 or the reverse.

The instrumented function behind the 304 numbers, cut to the lines that decide each row (`?mode=` picks the row; `cache=0` sets `useCache: false`):

```ts
const inm = url.searchParams.get('qinm') ?? request.headers.get('if-none-match') ?? request.headers.get('x-dh-inm') ?? undefined;
if (mode === 'none' && inm) return new Response(null, { status: 304, headers: { ...base, etag: inm } });     // probe: checks nothing, echoes
if (mode === 'head') {
```

`strip` drops a leading `W/`. The `|| inm` fallback is what sent `ETag: *` above. Two of the 140 relayed reads it logged, the same weak etag sent to the same file: `{"passed":"W/\"333d…\"","statusCode":304,"etag":"\"333d…\"","streamPresent":false,"xVercelCache":"HIT"}` and `{"passed":"W/\"333d…\"","statusCode":200,"etag":"W/\"333d…\"","streamPresent":true,"xVercelCache":"HIT"}`.

Caching between the function and the store: reads go through Vercel's CDN cache by default. `vercel.com/docs/vercel-blob` (Caching, Important considerations when updating blobs): "When you delete or update (overwrite) a blob, the changes may take up to 60 seconds to propagate through our cache." The same page says a server reading a private blob "can skip the propagation delay entirely and read the latest version with a consistent read" (`useCache: false` bypasses the cache, at the cost above). No read after a delete was run here: the test's deletes were followed only by `list`, which no longer showed the deleted paths. The build-pointer design never overwrites a served path, so the default cache is right only if a deleted path is never written again within that window with other bytes. If a client or project slug is reused and build ids can repeat, a read of a recurring path can, by that doc, get the deleted file's bytes for up to 60 s, which may be another client's. A build id unique for the life of the store (the `get` row above) rules this out too. The pointer itself is not in Blob: it is `build` on the project's record, which is stored through the `KV` port.

So no route was found that skips the middleware. That is no reason to trust it: Vercel's own private-storage page says "avoid relying on middleware for auth … always verify auth directly in your route handler, right next to the code that reads the blob". S5 stands: the files function checks the session and the host itself.

**But a request can choose which deployment answers it.** Vercel's Skew Protection sends a request to an older deployment of the same project when the request names that deployment's id. All three forms Vercel's docs name worked from `curl` with the test credential, on the custom domain and on the production alias: the query parameter `?dpl=<id>`, the header `x-deployment-id: <id>` and the cookie `__vdpl=<id>`. Pinned to the project's first deployment, `/api/file` answered from that deployment's function: the response carried `x-saw-credential`, which only the first version of `api/file.ts` sets (on every response, `'x-saw-credential': request.headers.has('x-dh-test') || /dhtest=/.test(request.headers.get('cookie') ?? '') ? 'yes' : 'no'`), and the request logs name the first deployment. The `api/file.ts` listed above is that first version, cut to the lines that decide a result: it leaves out this header, an `x-fn-host` header, the `x-blob-cache` header (the store's `x-vercel-cache`, which the timing table's first rows read as `HIT` or `MISS`) and the `console.log` that wrote the function log lines quoted from it (`fnlog=…`). Pinned to a deployment from the middle of the list, that deployment's middleware ran. Without the credential, the same pinned requests got `401` from the old deployment's own middleware (the logs name it). So pinning skips no gate; it chooses which gate and which function run. Unpinned requests, a made-up id, and a pinned request with `Origin` set to another site and `sec-fetch-site: cross-site` went to the newest deployment. A request with a browser's navigation headers (`sec-fetch-dest: document`, `sec-fetch-mode: navigate`, `accept: text/html…`) was not pinned by any of the three forms; with `sec-fetch-dest: document` alone it was. Both exceptions are documented (`vercel.com/docs/skew-protection`): "Skew Protection doesn't pin full-page navigations. When the browser makes a top-level document request, such as a hard refresh, entering a URL in the address bar, or opening a link in a new tab, Vercel serves the latest production deployment. This applies whichever way the request carries the deployment ID: the `?dpl=` query parameter, the `x-deployment-id` header, or the `__vdpl` cookie." (Document navigations), and "By default, Skew Protection ignores the deployment ID on cross-origin requests." (Allowed domains for cross-site fetch). Which request headers Vercel reads to tell either case was not isolated: the cross-site request sent `Origin` and `sec-fetch-site` together. So a person opening a link is not pinned, but a script is, a `fetch` from a page included. The decisive lines, on the custom domain (the production alias gave the same):


### What (a) means for the contracts

- **`Files`**: `put(path, body, type)`, `list(prefix)` and `remove(paths)` map one to one onto `put`, `list` (with paging), `del`. `get(path)` returns body, type and etag, and takes no `ifNoneMatch`. Its `etag` is never the store's, which is strong, weak, `''` or missing depending on the encoding and the cache (the `get` and `get` with `If-None-Match` rows). **The etag, defined here once:** `"<hash of path>"`, which the function sends as a strong etag, whose value is a hash of the file's full store path, `c/<client>/<project>/<build>/…`. The path holds the build id, so nothing is added beside it, and it is the same on every `get`. **The client does not always get it strong, so the function compares weakly.** When Vercel's edge compresses the function's 200 it weakens the etag. Requested with a browser's `Accept-Encoding: br, gzip`, an HTML file, a JS file and the 200 KB random `big.bin` all came back `content-encoding: br` with a weak etag, each its own value with `W/` in front (the random file 27 bytes larger than sent, so incompressible bytes are no exception); with `Accept-Encoding: identity`, or with none (as curl sends by default), no `content-encoding` and the same values strong. The function's 304 carried the strong form in every case, so a client can hold either form. The function therefore strips a leading `W/` from both its etag and each value sent before comparing, splits a list on commas (a comma is legal inside an etag value in general; harmless here while the path etag is hex, as the scratch one was) and compares each entry, and answers `*` only as the next point allows. Sent back exactly as received, `W/` included, the relayed value got the function's 304 (its log: `fn=304`) for all three files and both encodings, only because the scratch function strips `W/`. Compared with plain equality, no browser's value for a compressed file would ever match, and nothing would visibly fail: the same repeat with the relay ignored still got a client 304, made by the edge from the function's full 200 (`fn=200`), so every repeat view would read the whole file from the store and section 4's repeat-view figures would not hold. It comes from one pure function of the path, and nothing else computes it: the adapter calls it for the etag `get` returns with the body of a 200, and the files function calls it for the comparison and for the etag on its 304. Two copies of the formula could drift; then the 200 carries one value, the comparison uses another, and no repeat view ever matches, with nothing visibly failing. One shared function rules that out. **This differs from the plan's port:** its `get(path)` returns the etag only together with the body, so a function that answers before calling the port has no port etag to compare or send. For the function to have the etag with no store call, the port must give it for a path without reading the store, for example by the adapter exposing that pure function beside `get`; the slice that builds the port settles the shape. That etag is safe only if a path never recurs with different bytes, and `put` without `allowOverwrite` refuses only a path that exists now. So `share` (a later slice) must make each build id unique for the life of the store, random or otherwise never reused, not a per-project counter that restarts when a project is deleted and made again; otherwise a returning browser gets a 304 for a deleted project's file, and for up to 60 s the store's cache may serve the deleted bytes (section 1, Caching). So a client never holds a store etag, and a store-side `ifNoneMatch` would have nothing to match (and the store honoured even a matching one in only 119 of 140 tries). The 304 is the function's, made after its own checks and before it calls the port (next point). Scope prefixes end in `/`.
- **Gate and files function**: the stand-in gate (section 1) measured about 40 ms first byte on a reused connection from next to `iad1` (39 ms median refusing, 43 ms passing a static file); today's `vercel/proxy.ts` was not measured. The function plus blob read adds about 40 ms warm (80 ms median for the 200 KB file on a reused connection, 115 ms on a new one). The function as written answers a `Range` request with a full `200` and no `Accept-Ranges`; the `Range` header does reach it, so it could answer `206` itself, but no `206` was ever sent through the edge (not tested). What a video player or a resumed download does with the full `200` was not tested. A test or client script that sees `403` with `x-vercel-mitigated` was stopped by Vercel's DDoS mitigation, not by the gate (section 1). The function re-checks the session and host (S5), sets `cache-control: private, no-cache` and the etag defined in the `Files` point above itself, on every 200 and every 304, and should not cache private files in Vercel's CDN (`s-maxage`), as Vercel's page warns. Behind a gate that passes with `next({ headers: { 'cache-control': 'private, no-store' } })`, as today's `pass` does, the function's own `cache-control` is what the client gets, on its 200, on its 304 and on the 304 the edge makes from its 200; a files response that sets none goes out `private, no-store`, which a browser never stores or revalidates (section 1, "Which `cache-control` the client gets"). Requirement for the slice that builds the studio site's gate: a test holds that a gated files response, requested with a browser's `Accept-Encoding: br, gzip`, reaches the client with `private, no-cache` and its etag (weak when compressed, the `Files` point above), and that a repeat sending back exactly the etag it received, `W/` included, gets the function's 304. Sent without `Accept-Encoding`, or with a hand-copied strong value, the test passes while browsers miss. For `cache-control`, today's `no-store` in `pass` need not change; for `set-cookie`, today's `pass` does not do what the plan needs. The gate's `next({ headers })` values reach the client on a 200 and, except `cache-control`, are dropped on every 304, the function's, the edge's or a static file's, `set-cookie` included: a 304 carried only `age`, `cache-control`, `date`, `etag`, `server`, `x-vercel-cache` and `x-vercel-id`, and a static file's 304 no `age` (section 1, "On a 304 the client gets none of the gate's headers"). Requirement for the same slice: the gate reissues the session on a response that reaches the browser, and a deployed test holds, with a Studio cookie and with a Client cookie, that a session past its 5 minutes, making a run of repeat file requests answered 304, costs one session-check read, not one per request, counted from the gate's log. A request can pick any deployment younger than 12 hours by its id (`?dpl=`, `x-deployment-id`, `__vdpl`) and gets that deployment's gate, function and env (S5 above), so a fix to the gate or the files function, or a rotated secret, is in force only once `studio deploy` has made the older deployments unreachable: the docs give a threshold (`skewProtectionBoundaryAt`, which may be refused on Hobby, where the docs offer no Skew Protection and pinning may not exist; not tested), deleting them (a sentence the page does not limit to a plan; not tested on Hobby), or turning Skew Protection off, none run here. The studio site's files function always sits behind the gate, so the gate relays it in a header of its own (`x-dh-inm` in the test), which it deletes from every request it passes on and sets only from `If-None-Match`, never from what the client sent (section 1). The relay is needed because the platform removes the header, not because of the gate: without the gate in front the function would get no validator at all. `Range` and `If-Range` do arrive, so a `206` would need no relay (a `206` through the edge was not tested). The scratch function answers `*` without knowing whether the file exists: its `mode=none` probe returns a 304 for any value with no check, and its store path passes `*` to `get` (section 1). The files function must send a 304, for `*` or for a list entry that matches its etag (it splits a list on commas and compares each entry weakly, ignoring `W/`), only for a path it has already established is a file of the live build, since a 304 tells the caller the file exists; how it establishes that without a store call (for example from a file list `share` records with the build) is for the slice that builds it, and was not tested.

```ts
import { next } from '@vercel/functions';
```

## 3. Test (c): a per-host domain on Cloudflare by API

### Calls that worked

1. Ask Vercel which record the host needs, before adding it:

```bash
vercel api "/v6/domains/dh-test.suits-sandals.com/config?projectIdOrName=dh-learn-studios" --scope sas-team
# recommendedCNAME: [{rank 1: "<project hash>.vercel-dns-016.com."}, {rank 2: "cname.vercel-dns.com."}]
# recommendedIPv4:  [{rank 1: ["216.150.1.1","216.150.16.1"]}, {rank 2: ["76.76.21.21"]}], misconfigured: true
```

The rank-1 CNAME is per project (other projects in the zone point at other `<hash>.vercel-dns-01x.com` names).

2. Find the zone, look for the name, create the record (DNS only):

```bash
CF=https://api.cloudflare.com/client/v4
curl -s -H "Authorization: Bearer $(cat <token file>)" "$CF/zones?name=suits-sandals.com"                  # → zone id
curl -s -H "Authorization: Bearer $(cat <token file>)" "$CF/zones/<zone>/dns_records?name.exact=dh-test.suits-sandals.com"   # → [] before (that run used plain name=, below)
curl -s -X POST -H "Authorization: Bearer $(cat <token file>)" -H "Content-Type: application/json" "$CF/zones/<zone>/dns_records" \
  --data '{"type":"CNAME","name":"dh-test.suits-sandals.com","content":"<project hash>.vercel-dns-016.com","proxied":false,"ttl":60,"comment":"design-hub studios learning test (c), scratch"}'
# → success, record id <record id>
```

The token (DNS edit on one zone) can also read that zone (`/zones?name=` and `/zones` both returned just it). A second identical `POST` failed with `success: false`, code `81053`, "An A, AAAA, or CNAME record with that host already exists". That was seen once and its output was not saved; it was not repeated, since that would mean creating a duplicate record. So `ensure` does not depend on the code (below).

The name filter: Cloudflare's API reference for listing DNS records (`developers.cloudflare.com/api/resources/dns/subresources/records/methods/list/`) documents `name` as an object, `{ contains, endswith, exact, startswith }`, with `exact` "Exact value of the DNS record name. Name filters are case-insensitive", so the query is `name.exact=<host>`; it does not document a plain `name=`. Both were run read-only on the existing record: `?name.exact=dh-test.suits-sandals.com` and `?name=dh-test.suits-sandals.com` each returned `success: true` and the one CNAME (`proxied: false`, `ttl: 60`), and `?name=dh-test.suits-sandals.co` returned 0, so plain `name=` matches exactly today. The adapter uses the documented `name.exact`.

3. Add the host to the project:

```bash
vercel api /v10/projects/dh-learn-studios/domains -X POST --scope sas-team -F name=dh-test.suits-sandals.com
# → { name, apexName: "suits-sandals.com", verified: true }
```

What was run covers one case only: the apex, `suits-sandals.com`, was already a domain of `sas-team`, and the add answered `verified: true` at once, with no TXT asked for.

What the docs say, not run (a run would need a domain held by another account, which was not approved):

- **When `verified: false` comes back.** The REST reference for adding a project domain (`vercel.com/docs/rest-api/projects/add-a-domain-to-a-project`): "If the domain is not yet verified to be used on this project, the request will return `verified = false`, and the domain will need to be verified according to the `verification` challenge via `POST /projects/:idOrName/domains/:domain/verify`." Its `verification` field is "A list of verification challenges, one of which must be completed … If `verification.type = TXT` the `verification.domain` will be checked for a TXT record matching `verification.value`." And `verified: false` means "it will not be used as an alias on this project until the challenge in `verification` is completed."
- **Which case asks for the TXT: an apex in use by another Vercel account or team.** `vercel.com/docs/domains/working-with-domains/add-a-domain`, "Verify domain access": "If the domain is in use by another Vercel account or team, you may be prompted to verify access to the domain with a `TXT` record. This will not move the domain into your account, but will allow you to use it in your project." The same section covers a subdomain whose apex another team holds: "It is always created at `_vercel` on the apex domain (`_vercel.example.com`)", and "If you remove a domain from a project and add it again, Vercel generates a new value, so update the record." The verify call can then fail with "There is an existing TXT record on the domain verifying it for another project", "The domain does not have a TXT record that attempts to verify the project domain" or "The TXT record on the domain does not match the expected challenge for the project domain" (`vercel.com/docs/rest-api/projects/verify-project-domain`).
- **A brand-new apex nobody on Vercel holds.** No page found says it gets a TXT challenge. The same "Configure the domain" section lists the TXT only "If the domain is in use by another Vercel account"; otherwise it asks for the A record (apex) or the per-project CNAME (subdomain). Whether the add answers `verified: true` or `false` in this case is not stated, so the code must read `verified` and not assume either.

So `verified: false` is not tied to "the team does not hold the apex": it means another account or team uses the domain, and the challenge to complete is the one the `verification` array names.

### What `ensure(host)` must do on Cloudflare

```text
ensure(host):
  target = Vercel GET /v6/domains/<host>/config?projectIdOrName=<studio>  → recommendedCNAME rank 1, trailing dot dropped
  zone   = studio.json's zone id, else GET /zones?name=<apex>             (exactly one, status active)
  classify(records):
    one CNAME, content ∈ {target, cname.vercel-dns.com} (case-insensitive, trailing dot ignored), proxied false → 'exists'
    anything else (A/AAAA, another CNAME, proxied: true) → refuse with what is there; never overwrite or delete
  1. found = GET /zones/<zone>/dns_records?name.exact=<host>             (look up first, always)
  2. found not empty                            → classify(found)
  3. found empty                                → POST CNAME { content: target, proxied: false, ttl: 60 }
       success                                  → 'added'
       any error, whatever its code             → GET again (step 1); not empty → classify; still empty → fail with the POST's error
then Host.addDomain(host); if verified is false, add the TXT it names at _vercel.<apex> (its own lookup and compare, below), then verify.
```

The TXT step is from the docs and was not run (no `verified: false` came back), and the steps above do not cover it: `classify` refuses any record that is not the one expected CNAME, so run as written on `_vercel.<apex>` it would refuse an existing TXT, and it would never add a second one. Several hosts may each need a TXT at that same name, so the TXT case needs its own lookup (`name.exact=_vercel.<apex>`, keeping the TXT records) and its own compare by name, type and value: a TXT with exactly the value `verification` names is `'exists'`; TXTs with other values at that name are left alone, not refused, and the one named is added beside them.

`proxied: false` matters, from the docs, not tested: a proxied record puts Cloudflare's certificate and cache in front of Vercel, and Vercel issues its own certificate by HTTP-01, which works "as long as the domain points to Vercel"; behind a proxy, "route `/.well-known/acme-challenge/*` to Vercel on port 80 without caching, authentication, rewrites, or proxy-level redirects. Alternatively, point DNS directly to Vercel; for Cloudflare, use **DNS only**" (`vercel.com/docs/domains/troubleshooting`, Common SSL certificate issues). DNS only is the one case run here. The record's `comment` field is a good place to say which studio made it, so `client archive` can find and delete only its own records.

### What (c) means for the contracts

- **`Dns`, `mode: 'per-host'`, Cloudflare**: as above, three Cloudflare calls and one Vercel read; needs a token with DNS edit on the one zone, kept in the studio folder's env file. The zone id can go in `studio.json` (not secret) to save the lookup.

1. **Blob Advanced Operations, 2,000 a month on Hobby, are the first wall.** Every `put` and every `list` is one. Under the plan's layout, `c/<client>/<project>/<build>/…` with a new `<build>` per share, every share puts every file; the etag (section 1) and the plan's slice 4 rule that a file of a build that is not the pointer's is 404 rest on that layout, and these findings keep it. One way to spend fewer puts, **not tested here and not picked for the plan**: content-addressed paths, `c/<client>/<project>/a/<hash>` with each build holding a manifest of path to hash, so a share uploads only files whose content changed (Vite's hashed `assets/` rarely do) plus the manifest. The page does not say when the double count applies, so whether a gate that only calls `next()` causes it is not known; it was not measured. 3. **CDN Requests and Function Invocations, 1,000,000 each a month on Hobby, are the third wall, and views spend them per file, not per byte.** Every file of every view is one gate run, one function call and one client CDN Request, a 304 included; a file read from the store adds a second CDN Request (Functions and Transfer rows). Per view of the 43-file build:
   - **As built** (every view reads every file from the store, section 1): CDN Requests 43 + 43 = 86, so 1,000,000 ÷ 86 ≈ 11,600 views; Function Invocations 43, so ≈ 23,250 views, or 86 and ≈ 11,600 if the gate's runs count (the docs do not say); Blob Data Transfer 1,111,871 bytes, ≈ 8,990 views. **Blob Data Transfer runs out first**, at ≈ 8,990 views (unless middleware doubles Fast Origin Transfer, which then runs out first at ≈ 4,500: point 2, or more than about 2.6% of store reads miss the store's cache, which ends Simple Operations first: below), and CDN Requests next, at ≈ 11,600 (with Function Invocations, if the gate counts).
   - **A repeat view answered 304 before any store call**: CDN Requests 43, ≈ 23,250 views; Function Invocations 43, ≈ 23,250, or 86 and ≈ 11,600 if the gate counts; no Blob Data Transfer. **Function Invocations run out first** if the gate counts, at ≈ 11,600 views; if not, CDN Requests and Function Invocations run out together at ≈ 23,250. The 304 halves the CDN Requests and removes the bytes, but not one invocation.
   - First views always cost the as-built amount, so a month of f first views and r repeat views fits while 86 × f + 43 × r ≤ 1,000,000 (CDN Requests) and 43 × (f + r) ≤ 1,000,000 (Function Invocations; 86 × (f + r) if the gate counts).
   - Point 2's 9,000 views a month, as built: 9,000 × 86 = 774,000 CDN Requests (77% of the quota), 9,000 × 43 = 387,000 or 9,000 × 86 = 774,000 invocations, and 9,000 × 1,111,871 = 10,006,839,000 bytes, just past 10 GB. All answered 304 as repeats: 387,000 CDN Requests and 387,000 or 774,000 invocations, no bytes.
   - **Blob Simple Operations, first 10,000 a month on Hobby**, are spent by store reads that miss the store's cache, not by hits: Simple Operations "Counts when a blob is accessed by its URL and it's a cache MISS, or when you retrieve blob metadata without downloading the blob", and "Cache HITs do not count as Simple Operations" (`vercel.com/docs/vercel-blob/usage-and-pricing`, Usage and Usage details; its worked example counts "30% cache MISSes of 2.5M downloads + head calls"). Every `head` is one. Point 2's 9,000 views as built are 9,000 × 43 = 387,000 store reads, so a miss rate of 10,000 ÷ 387,000 ≈ 2.6% uses the quota up; at Blob Data Transfer's own limit, 8,990 × 43 ≈ 386,600 reads, it is the same 2.6%. So "Blob Data Transfer runs out first" holds only while fewer than about 2.6% of store reads miss the store's cache. That rate was not measured: in section 1 every first read of a new file was a `MISS` and the reads after it `HIT`s. How long the store's cache keeps a file, from `vercel.com/docs/vercel-blob` (Caching): "Vercel's CDN cache caches all blobs (private and public) for up to 1 month by default. You can customize this duration by setting a cache max age when you upload a blob." The same page (Simple operations): "A cache MISS occurs when the blob is accessed for the first time or when its previously cached version has expired." "Up to" is a ceiling: the page does not say a file stays cached that long or how often one is dropped sooner, and neither was measured. If a file did stay cached for the month, each file still being viewed would miss about once a month after its first read, so a live 43-file build about 43 times a month, far under 2.6% of 387,000 reads; that is arithmetic on the doc's ceiling, not a measured rate. A share's first views miss at least once per file, 43 per share, which alone allows 10,000 ÷ 43 ≈ 232 shares a month, more than point 1's 45. Past the quota all Blob access stops for 30 days, as for the other Blob quotas.
   - Past the Functions allowance the whole Hobby team is paused: every deployment, so every client's address, answers `503 DEPLOYMENT_PAUSED`, and it "doesn't resume on its own" (Functions row). That is worse than the Blob wall, which lifts after 30 days.

   For S14: if the gate counts as an invocation, a free studio serves at most 1,000,000 ÷ (2 × files per view) views a month across all its clients, ≈ 11,600 for the 43-file build, however well repeat views are cached, because each file served costs one gate run and one function call. If it does not count, the ceiling is 1,000,000 ÷ files per view, ≈ 23,250, reached only when nearly every view is a repeat answered 304 before any store call; as built it is ≈ 8,990 (Blob Data Transfer), or ≈ 4,500 if middleware doubles Fast Origin Transfer. Design to that count of files served, not only to bytes: a 304 before any store call saves Blob Data Transfer and the store's CDN Request, and nothing else.
4. **Per-host DNS caps a Hobby studio at 50 hosts on one project**: `studio.<apex>` plus 49 clients, assuming the project's own `.vercel.app` name does not count toward the 50 (the limit says "custom domains"; not tested). A wildcard was one entry in the project's domain list (test b), though the docs do not say how it counts toward the limit. The wildcard is not only for an apex on Vercel nameservers: the docs also allow it with `_acme-challenge` delegated to Vercel by `NS` records at another DNS provider (section 2, `Dns`; docs, not tested). So the 50-host cap binds a studio only where neither wildcard route is possible or the studio chooses per-host. `client add` on per-host should say how many are left.
