# Collaboration: people, access and what clients see

Status: slice 1 shipped in 0.6.0 (section 9 records what was decided in review), slice 2 in 0.6.2 and slice 3 in 0.7.0 (section 10 records what was decided in the build and its two second reads); slice 4 in 0.8.0 (section 11 records what was decided in the build); slice 5 in 0.9.0 (section 12 records what was decided in the build); slices 6 and 7 are planned. Sections 3 to 7 are a proposed design for the decisions in section 2. Two points stay open (section 8); both are answered by the exploration in slice 6 and block nothing before it.

## 1. Problem and success

Found by running the whole flow: invite, comment, manage the review.

- The Comments button is always on screen, above the prototype. It and the pins cannot be hidden.
- An invited person cannot tell how to get back in. The copied link says nothing about what it does. Neither the client nor the studio is told that a shared password exists or what it is for.
- Everyone who gets in sees everything. A comment, a prototype or a dial cannot be kept inside the studio.
- The review UI is unrefined next to the rest of the hub.

| It is working when | Measured by |
| --- | --- |
| A used or forwarded link opens nothing | Gate test: second use of a link answers 404 |
| No password page exists | `GATE_PASSWORD` appears nowhere in the repo; an anonymous request gets the sign-in page |
| A Client can never fetch anything internal | Service and gate tests: every read and write path refuses an internal thread, prototype and file to a Client session |
| Comments get out of the way | One action hides the button and pins, and the choice is remembered |
| A first-time client finishes the flow alone | Miles's walkthrough (open link, comment, come back the next day, resolve) completes with no help |

## 2. Decisions

| # | Decision | Reason |
| --- | --- | --- |
| D1 | DialKit is for prototype tuning only: dials, variants, View tools. Collaboration keeps its own UI. | The review layer is already separate (`shell/review/`); the gaps are in its UI and flow, not in DialKit. |
| D2 | Two kinds of people, **Studio** and **Client**, replace editor and reviewer. No viewer. | One label per person; "editor" never said which side someone is on. |
| D3 | Every person is named. No anonymous access. | Studio knows exactly who can see the work and can remove one person. |
| D4 | The shared password is dropped everywhere. | Nobody understood it, it never protected an invite link, and changing it signs everyone out. |
| D5 | Default sign-in is a **one-time link**: it signs in one device, then stops working. A second device gets a second link. | A leaked link opens nothing, with nothing to explain to the client. |
| D6 | A signed-in device stays signed in for the length of the engagement (3 months, 6 months, or open-ended). The project sets a default at setup or by a prompt to Claude, and Studio can override it for one person. | Engagements run for months; a short-term reviewer should not keep access as long as the main client. |
| D7 | Email sign-in (a one-time code through Resend) is an option a project adds, not a second setup. It turns on when Resend is connected. | One code path per release; one step, and it cannot be half on. |
| D8 | With email sign-in on, one-time links are off and every person has an email on record. | A leaked link is then never a way in. |
| D9 | The People tab says how links behave and offers a prompt to copy for Claude that upgrades the project to email sign-in. | The team learns the trade-off at the moment they share. |
| D10 | One pair of words, **internal** and **client-facing**, applies to a comment, a prototype and a dial. | Three objects, one rule to learn. |
| D11 | A Studio comment is internal and stays internal. To tell the client, Studio writes a new comment. Clients never receive internal ones. | Production notes stay inside the studio, and no reply is ever exposed by a later switch. |
| D12 | Studio sees all comments by default, each thread marked with its audience, with a filter to narrow. | A missed client comment costs more than a crowded list. |
| D13 | A new prototype is internal. Studio marks it client-facing with a switch in the hub. | Private features must not leak by default, and Studio can share without a redeploy. |
| D14 | Internal prototypes are split and refused: their code and text load only for Studio, and the server refuses those files to a Client. | Hiding them in the index would leave names and code in the client's browser. |
| D15 | A dial is internal until marked client-facing. The marking workflow is explored first, in the hub and in code. | Safer default; the workflow is a product-experience problem. |
| D16 | View tools (theme, reduce motion, speed) are always available to Clients. | They change how a client looks at a prototype, not the design. |
| D17 | Studio has a **Client view** that shows the hub exactly as a client gets it. | Checking that work is client-ready before a presentation. |
| D18 | A Client can resolve and reopen any client-facing thread, not only their own. | Clients work with others in their own organisation. |
| D19 | Clients do not manage people. Studio adds and removes them. | Follows D2: Miles's list of what a Client does has no people management. |
| D20 | Start clean: no migration of people, comments or sign-ins. | Nothing is live; there is one test account. |
| D21 | Later work, in the backlog: tagging a person in a comment, and comment notifications by email. | Out of scope here. |

| `core/review/policy.ts` | Rules by role and ownership | Rules by kind, ownership and thread audience |

| `server/api.ts` | Ops return everything to any signed-in person | Reads take the caller's kind, or `client` in Client view; new ops list the visible prototypes and set a prototype's audience |
| `shell/review/` | One 989-line file, own styles, always-on launcher | Split by part, built on `kit/ui`, hideable, audience on threads, Client view, People tab disclosure |
| `vite/registry.ts`, `shell/registry.ts`, `shell/Index.tsx` | Every README inlined in one bundle; index built from it | Each prototype's README and code in files named for it, loaded on demand; index built from the server's list; a Studio switch per prototype |
| `kit/ViewTools.tsx` | Shown to everyone | Unchanged: always client-facing (D16) |
| `kit/dials.tsx`, `kit/Variants.tsx` | Every control shown to everyone | Internal by default; marking per slice 6 |
| `scripts/` (`people`, `share`, `bootstrap`, `comments`) | Password set at bootstrap and returned by `share` | No password; access length flags; kind on people; audience in pulled comments |
| `server/mailer.ts` (new, slice 7) | none | One port for sending mail; Resend behind it |

Contracts that change:

- **Store keys** (`core/review/store.ts`): a new key prefix, so old records are ignored (D20). People, links, comments per prototype, plus settings (default access length), counters (thread numbers), prototype audiences, and email codes (slice 7).
- **Gate responses**: an anonymous page request gets the sign-in page (401). `/invite/<token>`: GET shows who the link is for, POST uses it up and sets the cookie. A used, expired or unknown link gets 404. A person past their access end is signed out. A Client asking for an internal prototype's page or files gets 404. Old cookies stop working.
- **Environment**: `GATE_PASSWORD` is no longer read. `GATE_SECRET` stays. Slice 7 adds the Resend key and a sender address; their presence turns email sign-in on.

## 4. Program design

Only where rework is costly: the stored shapes, the rules, sign-in, and the prototype boundary. Every later slice reads these.

```ts
// core/review/model.ts
type PersonKind = 'studio' | 'client';              // replaces Role
type Audience = 'internal' | 'client';
type Person = { id; name; team; kind: PersonKind; email: string | null;
                accessEndsAt: string | null; createdAt; revokedAt; epoch };
type Comment = { /* as today */ audience: Audience; number: number };   // both on roots; replies follow the thread
type Link = { person: string; expiresAt: string };  // unused-link lifetime as today; deleted when used

// core/review/policy.ts
type Action = 'read' | 'comment' | 'edit' | 'delete' | 'resolve' | 'triage' | 'people' | 'audience';
function can(actor: Person | null, action: Action, root?: Comment, subject?: Comment): boolean;
function visibleTo(viewAs: PersonKind, comments: Comment[]): Comment[];

// core/review/service.ts (changed and new members)
addPerson(actor, input): Promise<{ person: Person; token: string }>;      // was invite; input may carry an access end
newLink(actor, id): Promise<{ person: Person; token: string }>;           // another device; sessions stay
signOutEverywhere(actor, id): Promise<{ person: Person; token: string }>; // was reissue
peekLink(token): Promise<Person | null>;                                  // GET
useLink(token): Promise<Person | null>;                                   // POST; deletes the link
listComments(actor, prototype, viewAs?: PersonKind): Promise<Comment[]>;
visiblePrototypes(actor, viewAs?: PersonKind): Promise<string[]>;         // slugs
setAudience(actor, prototype, audience: Audience): Promise<void>;         // Studio only
audienceOf(prototype): Promise<Audience>;                                 // absent means internal

// server/session.ts
type Gate = { secret: string };
issuePersonToken(gate, claim: PersonClaim, endsAt: string | null): Promise<string>;
```

Call trees:

- **Sign-in.** `proxy` on `/invite/<token>`: GET calls `peekLink` and renders who it is for. POST calls `useLink`, then `issuePersonToken`, sets the cookie and redirects.
- **Any request.** `proxy`: `readPersonToken`. A stamp under 5 minutes old passes on the signature; an older one asks `sessionPerson` (revoked, epoch, access end) whatever the request's headers say, then passes with a re-stamped cookie, or answers the sign-in page (section 10).
- **A prototype's page or file.** `proxy` reads the slug from the path or the file name; for a Client it calls `audienceOf` and answers 404 when internal. Studio skips the lookup.
- **Any API op.** `handleReview`: `actorFrom`, then the service, where `can` and `visibleTo` decide. The browser never filters.

File naming is the prototype boundary: everything built from `prototypes/<slug>/` (code, README, CSS, images) lands in files that carry the slug in their name, so the gate refuses by name with no build manifest.

Rule table `can` must satisfy, tested row by row:

| Action | Studio | Client |
| --- | --- | --- |
| read, comment, reply | any thread | client-facing threads only |
| edit | own | own |
| resolve, reopen | any | any client-facing |
| delete | any | own |
| triage, people, prototype audience | yes | no |

A Studio comment is internal; a Client comment is client-facing. A Studio reply in a client-facing thread is client-facing.

Not designed here, and why:

- **Comment UI (slice 1)**: visual, judged by eye, cheap to change. Only the file split is fixed.
- **CLI flags, docs, skills**: the contract is already fixed by `scripts/lib/cli.ts`.
- **Dials (slice 6)**: the exploration is the design step.
- **Email sign-in (slice 7)**: sits behind one port, designed after a learning test proves how Resend behaves. Only `Person.email` is needed earlier, and it is above.

## 9. Slice 1: decided in review

Chosen from four directions on a live picker (Current, Quiet, Spatial, Conversation), with hostile fixtures: Spatial.

- **No panel.** One round button (40px) turns comment mode on. Off, the page carries only the button and its open count.
- **Comment mode.** Pins appear; a click anywhere starts a comment in a card beside the click, and a click on or near a pin (16px) opens its thread. A bar at the bottom is one quiet pill in three groups with hairline rules between, nothing filled: a Pin / Page toggle (the chosen half is the bar's one fill; Page opens a comment on the whole page, Pin or a click on the page goes back), a stepper (‹ 2 open ›, then ‹ 1 of 2 ›) that steps straight through the threads, and ⋯ (Show resolved, People for editors, Hide comments) with × to stop. Esc steps back: the card, then the mode.
- **One thread at a time** in a 320px card beside its pin, flipped and clamped on screen, stepped with the bar's arrows (the phone sheet carries its own, since the bar steps aside for it); a thread with no pin on this view sits beside the button. Reply box and Resolve in the foot; kind and state as two small selects for editors.
- **Open and resolved differ at a glance.** Open pin: 24px, solid, numbered. Resolved pin: 20px, pale, a check. Resolved card: check badge, a band naming who resolved it, muted text, Reopen in place of the reply box. The check is the layer's one hue.
- **The button moves.** Drag it and it glides (380ms, `--ease-drawer`) to the nearest of six spots: four corners and the middle of each side, projected 120ms along the release velocity. Alt and an arrow move it by keyboard. The spot and the hidden state are remembered per browser.
- **Text box.** Grows with its words; Enter sends, Shift Enter breaks a line.
- **Nothing over the page.** Comment mode catches a click or tap at the document before the page sees it, instead of laying a surface over it, so the page and its own panels still scroll by wheel and finger. A keyboard comments on the focused element with Enter.
- **On a phone** (560px and under): the card is a bottom sheet with a grab handle, dragged down by its head to dismiss (past 96px, or a flick over 0.5px per ms), lifted over the iOS keyboard through `visualViewport`, padded for the home indicator. The bar docks to the bottom edge as a toolbar and the button steps aside while comment mode is on. A pin the sheet would cover scrolls up into view.

Rejected:

- **Quiet** (one-line rows that open in place, in a panel): least to read per thread, but still a panel over the page, and two clicks to a reply.
- **Conversation** (a docked text box, drill-in threads): easiest first comment, but it hides where a comment points and the kind and state.
- **Current** (cards with every control shown): six controls per thread, two full-width controls before the first comment, and a full-height panel for one comment.

Left for later slices: an audience mark on the card header and a third pin face for internal threads (slice 4).

## 10. Slice 3: decided in the build

Built by one agent, read twice by a second model. The first read found that a revoked cookie still loaded pages; the second found nothing that passes the gate. What the code now does where section 4 said less or said otherwise:

- **The session is re-checked every 5 minutes, on every kind of request.** Section 4 had only pages ask the store. A request's headers are the client's to choose, so a revoked cookie sent without `sec-fetch-dest: document` loaded every page and file until the token expired. The token is now `p3.<id>.<epoch>.<expires>.<checkedAt>.<sig>`. Under 5 minutes since the store's last yes (`CHECK_SECONDS`), the signature is enough. After that the gate asks the store on the next request of any kind and re-issues the cookie with a new stamp and an expiry from the person's current access end. So a revoke, a sign out everywhere or a changed access end reaches a signed-in device within 5 minutes; a link stops at once. The API asks the store on every call.
- **The token is signed to the site.** The review store's URL is in the signed message (`Gate = { secret, site }`), so two projects with one `GATE_SECRET` never accept each other's cookies.
- **A store that does not answer is 503, never a sign out.** Links work once, so clearing cookies on an outage would lock everyone out. The cookie is cleared only when the store answers no.
- **A person is three records.** A profile (`people`), a write-once revocation (`revoked`) and an epoch only ever raised by `HINCRBY` (`epochs`). The last two overrule the profile, so a write that started from a stale read cannot undo a revoke or a sign out everywhere. `KV` gained `hincrby`, and `hdel` returns its count.
- **Using a link.** Read and check the link and person, delete the link (the count is the claim, so two POSTs sign in one device), then read the person again and refuse if a revoke or sign out landed in between.
- **Access length.** `3m`, `6m` or `open`; the project default is `3m` when unset and lives in the store's `settings`. A Client gets the default, a Studio person open-ended, either can be overridden, and `setAccess` changes one person later. Month ends clamp (30 Nov plus 3 months is the last day of February). A session never outlasts 400 days, the browser's cookie cap; the re-issue renews it while access holds.
- **The review store is required.** People and links live in it, so a deployed site without one has a gate nobody can pass. `preflight` and `share` refuse before any deploy, and `share` probes a made-up link after one.
- **Old state.** Store prefix `hub3:`; `p1` and `p2` tokens and the old gate cookie never verify. An upgraded project adds everyone again (`miles-deploy` says how).
- **Words.** Service: `addPerson`, `newLink`, `signOutEverywhere`, `revoke`, `setAccess`, `peekLink`, `useLink`. API: `people.add`, `people.link`, `people.signOut`, `people.revoke`, `people.access`, `access`, `access.set`. CLI: `people add | link | sign-out | revoke | access`, `--access`.
- **The link page** sends `Referrer-Policy: same-origin`, so Continue carries an Origin on browsers without `Sec-Fetch-Site`; every other gate page sends `no-referrer`.

Slices 4 and 5 build on these: a new read path goes through the composed person, and slice 5's refusal of an internal file sits after the session check in `proxy`, where the store is already asked at most once per 5 minutes per device.

Left in the backlog: a double press on Continue, a rate limit on `/invite/*`, earlier deployments that keep the password page, two sign outs at once, the comment-id answer to a signed-out caller, the local store across two processes.

## 11. Slice 4: decided in the build

Built by one agent; the human read of every service read path is still to come. What the code now does where section 4 said less or said otherwise:

- **Audience and number on every comment.** Section 4 put both on roots. A reply copies its thread's `audience` and `number` when it is written, and nothing changes either afterwards, so the copy cannot drift. The rule is one line: a comment's audience and number are its thread's. `audience` is `'internal' | 'client'`; the UI and the docs say Internal and Client-facing.
- **Who sets the audience.** A Client's new thread is client-facing whatever the request says. A Studio thread is internal unless `add` gets `audience: 'client'` (the new-comment card's choice, Internal first). A value outside the two is `invalid`, for either kind. A reply takes its thread's; nobody sets it. The rule lives in `audienceFor` in `policy.ts`.
- **Numbers.** Per prototype and audience, from `hub3:counters`: field `<prototype>` for client-facing threads, `<prototype>:internal` for internal ones, raised by `HINCRBY` when the root is made, so two threads at once get two numbers and a failed save skips one. Internal and client-facing are separate kinds, so they count apart and a Client never sees a gap where an internal thread sits. `threadLabel` names them in words: `I2` internal, `2` client-facing, in screen-reader labels and `comments pull`. The pin and the card badge show the bare number; their amber says internal. A number is never reused: a delete moves no other. Threads numbered while one count served both (0.8.0) keep their numbers; the internal count starts past the highest internal one there. The panel's pins and cards read `number`, never list position.
- **Old records.** No migration and no prefix change. Every comment the service reads goes through `readComment`: a record without `audience`, or with any other value, reads as internal, so a missing field never shows a Client anything; a record without a positive whole `number` reads as 0, which the panel shows as a pin with no number and the pulled file as a line with no `#`. Nothing is written back.
- **The rules.** `can(actor, action, root?, subject?)`: for a Client, any action on a thread or reply that is not client-facing is refused, before the table is read. Ownership reads the subject, else the root. `visibleTo(viewAs, comments)` keeps, for a Client, the client-facing roots and the client-facing replies whose root is among them, so a reply never outlives its thread's audience. `viewOf(actor, viewAs?)` is the view a person gets: Studio, or Client when Studio asks; a Client asking for Studio's still gets a Client's, and nobody signed in gets a Client's.
- **No comment leaves the service unfiltered.** `listComments(actor, prototype, viewAs?)`, `allComments(actor)` and `locate(actor, id)` each take an actor. Ops by id (`reply`, `edit`, `remove`, `resolve`, `retriage`, `locate`) find the comment and its root through one helper, `seen`, which answers only when `can(actor, 'read', root, comment)` holds. A Client naming an internal thread or reply gets `not_found`, "No such comment.", the same as an id that is not there, never `forbidden`. A reply whose root is gone is not found either. `retriage` stays `forbidden` for a Client whatever the id, because triage is Studio's and that answer says nothing about the id. `remove` names in its answer only what the actor may see.
- **A signed-out caller is refused before any lookup.** Every op by id now checks the actor first, so a caller with no session gets `unauthorized` whether or not the id exists. This settles the comment-id answer to a signed-out caller that section 10 left in the backlog.
- **Client view.** The API's `comments` query takes `viewAs`; an unknown value is 422 (`viewAs: one of studio, client`). Writes ignore it: a Studio person in Client view still writes as Studio, and the panel sends a new thread there as client-facing. The panel fetches with `viewAs=client`, judges every control as if the person were a Client (Studio's controls step aside, and no audience words show), and puts a plain note over the bar with **Leave**. Client view is remembered per browser (`proto:client-view` in `kit/prefs.ts`) for slice 5 to reuse on the index; a Client's stored value changes nothing, since the server gives them a Client's list anyway.
- **Studio's filter.** All, Internal or Client-facing in **⋯**, in memory like Show resolved, and gone in Client view. It narrows what the server already sent Studio; it is never what keeps a comment from a Client. While it is not All, a note over the bar, in the same quiet pill as the Client view note, says **Internal only** or **Client-facing only**, with **Show all** to set it back (`filterNote` in `view.ts`). The bar's stepper counts the narrowed list; the round button's open count, shown with comment mode off, always counts every open thread the person was sent, so a filter cannot hide that a client comment is waiting (D12).
- **The pin faces.** Open: solid and numbered. Open and internal: numbered on amber, the colour support tools give an internal note, the colour alone telling it apart, and far lighter than the open face so it reads apart without the hue. A dashed grey edge read as a draft. Resolved: small, pale, a check, whatever the audience. The card's number badge and Internal tag carry the same amber.
- **The pulled file.** Each thread line in `comments.md` opens with `#I<number> (internal)` or `#<number> (client-facing)`. `comments summary` counts internal and client-facing threads per prototype beside open and resolved.

## 12. Slice 5: decided in the build

Built by one agent and read twice by a second, whose findings (the build boundary, the gate's path parsing, comments on an internal prototype, the shell, then ownership by source in place of matching on text) are fixed here; the human read of the file naming and the gate rule is still to come. What the code now does where section 4 said less or said otherwise:

- **The learning test.** On Vite 8.3.5 (Rolldown) with the config before this slice, only a prototype's entry chunk and its CSS carried the slug, and by accident: lazy sub-chunks (`Heavy-<hash>.js`) and images (`bg-<hash>.png`) did not, every README sat in one shared chunk, and the main bundle held a map of every slug. What holds instead, proved end to end and now built: one virtual entry per prototype (`virtual:design-hub/entry/<slug>`: its README raw and a `load` for its `index.tsx`), emitted by the registry plugin as its own chunk with a fixed file name and `preserveSignature: 'strict'` (without it the file is empty), and `chunkFileNames` and `assetFileNames` as functions of what each file holds (a chunk's module ids, an asset's original files). Section 4's "files that carry the slug in their name" became files under the slug's folder.
- **The layout.** Everything built from `prototypes/<slug>/` (README, code, CSS, fixtures, lazy chunks, images) lands in `dist/_p/<slug>/`; the entry is `_p/<slug>/entry.js`, without a hash, since the gate sends `private, no-store` on every pass. `_p` can never be a slug, because SLUG has no underscore. Shared code (the kit, React, the hub) stays in `assets/`, and no file outside `_p/<slug>/` refers into it. The main bundle fetches an entry by path, so it holds no map of slugs. The walkthroughs are the exception, left in the backlog: their compiled text and every feature's name sit in `assets/` and go to every signed-in person, so a walkthrough must not name or describe internal work until that is built (the template's `AGENTS.md`, `miles-prototype`, `miles-new-feature` and the guide say so).
- **What the build check is for.** It stops an author's or an agent's mistake: a prototype that reads another's files, the kit or the hub that reads a prototype's, prototype content written where every signed-in person loads it. It is not what stops a Client: the gate is (it refuses an internal prototype's page and every file under `_p/<slug>/`), so a reach the build missed exposes a prototype only by putting its content in a file outside its folder. One rule runs through every recorder: one that sees nothing fails the build, never answers "the hub's".
- **A built file is owned by where its content comes from, never by who reads it, and the sources are recorded, not inferred.** Each source is recorded as the build writes the file: a stylesheet's CSS modules in `renderChunk` (order post, after Vite writes each chunk's sheet and before it moves a CSS-only chunk's sheet onto its importers; on Vite 8.3.5 each chunk's `importedCss` then holds only its own sheet), with the owner of the chunk that wrote it; an asset's original files; a worker's output, as the kit's only when every module and file it came from is outside `prototypes/`. Which modules make a sheet is Vite's own test (`vite:css`: not `?inline`, `?raw`, `?url`, a worker, `?transform-only`, exact parameters), so `?no-inline` or `?theme=raw` is a sheet. A sheet with no CSS module recorded, or any written file with no record and no fixed name (`_p/all.js`, each `entry.js`, `_gate/*`, `index.html`), fails the build, naming it. Owned only by prototype `a`: it lives in `_p/a/`. Owned by nothing under `prototypes/` (the hub, the package kit, the project's `kit/`, node_modules): it lives in `assets/`, once, never copied into a prototype's folder; a prototype's files read the `assets/` copy. Nothing under `prototypes/` is ever the hub's: a file directly there, or in a folder with no README, is owned by its own name, and importing it fails in dev and in a build with "shared code belongs in kit/"; a folder with a README alone is a prototype. The same bytes from several owners: one copy per owner, each owner's files pointed at its own. A copy keeps the name Rolldown made safe while every source of it and the chunk that wrote it are its owner's; otherwise it is named from its owner's own source (file or CSS module), made safe the same way (`half50%.png` is `half50_-<hash>.png`). So no copy carries a name from another owner's file, and nothing in `assets/` is named for anything under `prototypes/`.
- **Kit and hub sheets.** A kit or hub sheet that only prototypes import is a chunk of its own (one `codeSplitting` group per file, named for its path, with a `debugName`), so it is the kit's alone and lives once in `assets/`. A prototype importing a sheet the hub itself loads changes nothing the hub writes: in a build that import goes through a stand-in, which is empty when the hub's entry loads the sheet statically (on every page, before any prototype) and imports it otherwise, so the hub's sheets and their order in `index.html` are the same with or without it. A kit CSS module's stand-in always passes on its default and named exports, so a prototype gets in a build the class names it gets in dev; `?inline`, `?url` and `?raw` of a kit sheet never go through a stand-in (and `@kit/<name>?url` resolves to the real path, since Vite turns it into `?transform-only` and resolves that on the real path itself; every other `@kit/` import keeps its path in `kit/`, so a `kit/` symlinked to a folder outside the project still resolves the project's own dependencies, a `BUILDS` row with `motion/react`; owners are decided on real paths either way). A chunk's sheets load in the order the source imports them, as in dev, for kit and own sheets alike: Vite puts a chunk's own sheet before the ones it moves onto it from CSS-only chunks, so a post plugin sorts them by where their CSS modules run (each module's static imports first, in import order) before Vite writes the preload lists, with one importer as with two. It sorts only a prototype's chunks: the hub's and the kit's keep Vite's order, and a test builds the sample project with and without the step and asserts every file outside `_p/` is byte for byte the same. A kit sheet a kit component imports goes where that component's code goes.
- **Nothing a prototype owns is inlined by the size limit.** `build.assetsInlineLimit` answers no for any file under `prototypes/` (Vite's 4 KB default otherwise). An author sees one change: a prototype's own small images and SVGs are files under `_p/<slug>/`, not `data:` URIs. `?inline` and `?raw` are answered by Vite before that limit; a prototype may use them on its own files, and a reach with them is refused below.
- **Reaches, refused where they are made.** Not a reach: the dependency scan, and Vite's own importer for every URL a browser asks for in dev and for every entry (the hub's `index.html`); both resolve each prototype's `index.tsx` from that page, and `pnpm test` starts the dev server on a cold cache to prove it logs no scan failure. In dev and in a build, on real paths in their on-disk letter case, and by the platform's own path rules (`path.relative`, not a `/` prefix, so a Windows path with backslashes from `realpathSync.native` and slashes from Vite has the same owner; a unit test feeds Windows paths to the Windows rules, `path.win32`, and nothing here ran on Windows) (a symlink into another prototype's folder is that prototype's; on a disk that folds case, `../../Prototypes/beta/x.css` is beta's, since `real` uses `fs.realpathSync.native`, which returns the case on disk where Node's own keeps the case as written; the `REFUSED` rows for an import, an asset import, a CSS `url()` and a kit file's `?raw` in another case skip, saying so, on a disk that tells case apart): any import into a prototype by a file that does not own it (a prototype, the kit or the hub; the registry's own modules excepted), whatever its query; any `new URL('…', import.meta.url)` whose target another owner holds, `?inline` included, found with the parser Vite itself uses (oxc, `parseSync`) on the code Vite's own `new URL` plugin reads (TypeScript and JSX already compiled, Vite not yet answered), so a quote in a regex literal or in JSX text hides nothing and a comment or a string that only looks like one builds; and inside every stylesheet, through a postcss plugin in Vite's own postcss run (`vite/css-boundary.ts`), a node inlined from another owner's file or a reference into one (`@import`, `url()`, the strings in `image-set()`, and in a CSS module `composes … from`, `@value … from`, `:import("…")`, those three followed through every module on disk). Each reference is unescaped as Vite unescapes it before resolving (a backslash before a character that is not a letter, digit or `_` is dropped, so `url(..\/beta\/x.png)` is `../beta/x.png`; Vite does not export the rule, so it is repeated, and a hex escape stays as written, as Vite leaves it), then followed as a path and through Vite's own resolvers (`createIdResolver` with the options `vite:css` gives them, so `resolve.alias` and package paths count, a symlinked package included; the `REFUSED` rows that prove the resolvers are a `url()` and an `image-set()` through an alias and a `url()` and a `composes` by a package path, each of which builds without them, while an `@import`, `composes`, `@value` or `:import` through an alias is refused by the inlined-node check or the plugins first, so no row of those tests the resolvers); the plugin container's resolver is not reachable from a postcss plugin, and `@kit/*` is not one of Vite's CSS aliases, so Vite leaves a `url(@kit/…)` as written, with a warning that it did not resolve. Only references count: a `content:` string is text, and comments never count. A stylesheet that postcss cannot parse fails the build, naming file and line and saying to fix it: skipping the check on a parse error would be a way round it. Plain Vite built some such sheets before; the upgrade note in `miles-deploy` says so. Sass, Less and Stylus are refused, in dev and in a build: an import of a `.scss`, `.sass`, `.less`, `.styl` or `.stylus` file from a prototype or from the project's `kit/` (by a script, or by a stylesheet's `@import`, `composes`, `@value` or `:import`, whatever query the stylesheet was imported with) fails, naming the file and saying to use plain CSS or `.pcss`, because their own `@import` and `@use` resolve inside the preprocessor, where no check sees them. `?raw` of one is allowed: it is read as text and never compiled. No project installed them.
- **Real reads, at the end of a build.** A read is one Vite records (a chunk's imports, `importedCss`, `importedAssets`) or a built file's hashed name in another built file's text (a preload list, a stylesheet's `url()`). Fixed-name files are never read for that, never moved, and prose that names them is never rewritten. A file that reads what another prototype owns, or a hub or kit file that reads what a prototype owns, fails the build, naming reader and source. With the checks above this rarely fires; it is the backstop.
- **What was written, whatever wrote it (`vite/leaks.ts`): a backstop for whole-file inlining, nothing more.** Every review round found a new Vite spelling past the input checks (`?inline`, `?raw`, workers, `@value`), so after settle the build also reads its output: a built file outside `_p/<slug>/` (`assets/`, `index.html`, `_gate/`, `_p/all.js`, another prototype's folder) that holds a **whole** file of `prototypes/<slug>/` fails the build, naming the built file, the source and the form. Exactly three forms count, the ones Vite 8.3.5 writes a whole file in (`vite:asset`): the built file is byte for byte the source (a copy); a `data:` URI anywhere in a built file (in a script, anywhere in one of its strings, as `?inline` CSS holds one) decodes to exactly the source, base64 or the URL-encoded SVG form (`svgToDataURL`, which Vite does not export, so its six replacements are repeated and the `LEAKS` row for it fails if Vite changes them); a string in a built script equals the whole text of a source the build read (every string read with `parseSync`, so escaping and quote style hide nothing). For the string form only, a prototype's file counts when it passed through the build: a load hook at `enforce: 'pre'`, which runs before Vite's own loaders (`vite:asset` answers `?raw` in `load`), records every prototype file loaded, `this.load` included, so a sentence in an unimported `tagline.txt` and the same sentence as JSX text in another prototype build. A copy and a `data:` URI are still compared with every source, since some of Vite's inlining calls no hook. Nothing else counts: no line, no CSS rule, no prefix and no other part of a file is looked for, so two prototypes that share a README line, a sentence of UI copy, an SVG path, a shader line or a rule (flat in one, nested in another) build, and so do two fresh scaffolds or a copied prototype. Nothing smaller than 40 bytes is looked for (`MIN`): an empty or trivial file (`.gitkeep`, `{"a":1}`) would match a short string by chance. A match is legitimate only when the reader's owner (the hub and the kit for a file outside `_p/`, that prototype for one under `_p/<slug>/`) has a source with the same whole content: the image in `kit/` and in two prototypes, the prototype font that is byte for byte Geist. The sources are every file under each prototype's folder on its real path (a symlink is skipped there and read as its target's owner's), except a prototype's own `node_modules`, of which only the files the build read count, and every file the build read from outside `prototypes/`. It is linear: each built file is read once (its hash, the hash of each data URI in it, the hash of each string over `MIN` in a script), and each source is hashed once by a streamed read, only when its size is one a built form has, so most sources are never opened. Two rules keep a file it cannot use from failing the build with a wrong message: a source it cannot open (mode 000), or a folder it cannot list, is skipped, since Vite could not have read it either; a source over 64 MB (`LARGE`) is compared only with whole built files, since Vite inlines a file into a script or a data URI only by reading it into memory, and is never read unless a built file has its size (a 3 GB recording beside a prototype costs nothing). A built script that does not parse fails the build. Proven by `LEAKS` in `vite/build.test.ts`: a test-only plugin loads a prototype's file through Vite (`this.load`, so Vite writes the form) and pastes it into the hub's entry, which no input check sees, for a base64 image (whole, and inside a longer string), a URL-encoded SVG and a `?raw` text with every quote in it; each fails the build only through this check. `BUILDS` holds the honest shapes above, including a product and a website app fresh from `design-hub new`, the brand sample beside a fresh brand prototype, a file nobody may read, a folder nobody may list, an unimported text file whose sentence is JSX text in another prototype, and a 3 GB file nobody imports. It does not catch: part of a file (`?inline` CSS, which Vite minifies, is one; so is a text cut or joined), compiled TS, JS or JSON (the chunk check's), content transformed on the way (a resized image), anything in dev (it reads a build), and a file read outside the build (a plugin's `fs` read of a prototype's `node_modules`). It costs about 0.1 s a build, measured around the call: 91 to 99 ms on the sample project (43 built files, 432 files read), and 494 to 522 ms on a generated project of 40 prototypes with a 270 KB `fixtures.json`, three 200 KB images and six SVGs each (547 built files, 35 MB), where the line and rule matching it replaces was measured at 32 s. An unimported 10 MB CSV beside a prototype adds nothing measurable (90 ms on a small project).
- **Workers.** Vite builds a worker without the hub's plugins, so every worker bundle gets a guard (`worker.plugins`): one at `enforce: 'pre'` that resolves every import first and refuses any module under `prototypes/` on its real path, queries stripped (`?raw`, `?inline`, `?url`, an asset import, a glob), and one at normal order that refuses any `new URL` into one, read with the parser as above. A worker's output counts as the kit's only when every module and original file it came from is outside `prototypes/`; an asset's original files are resolved against Vite's root, where Rolldown names them. A worker in a prototype stays refused; a kit worker that touches no prototype builds whoever uses it. `@kit/<name>?worker` resolves through the kit resolver, and every worker bundle has the kit resolver too (`worker.plugins`, after the guard), so a kit worker's own `@kit/format` import is bundled, not left external.
- **The build proves its own boundary.** It also fails if a chunk holds two prototypes' modules or one prototype's outside `_p/<slug>/`. `vite/build.test.ts` runs a real build of a fixture with sentinels in every kind of file, then three tables, each row a small build of its own: every reach that must fail (`REFUSED`), every leak only the output check sees (`LEAKS`), and every honest shape that must build (`BUILDS`). It asserts no hub or kit sheet sits under `_p/` or exists twice, that the hub's sheets and their order do not change when a prototype imports one, and that the build raises no file-name conflict and no code-splitting warning.
- **Limits an author must know.** Said in the template's `AGENTS.md` and `miles-prototype`: `pnpm dev` runs the import, `new URL`, stylesheet and Sass checks but not the end-of-build read and output checks, so run `pnpm build` before sharing; a `new URL` whose path is built at run time (not a literal) is not seen at all, by Vite or by the build, unless its content lands outside the prototype's folder, where the output check finds it.
- **Vite is pinned to its minor.** The boundary leans on Vite internals: `vite:css-post` writing a chunk's sheet in `renderChunk`, `viteMetadata.importedCss` and `importedAssets`, `options.scan`, `<root>/index.html` as the default importer, `parseSync` and `Visitor` exported from `vite`, `createIdResolver`, and the forms in `vite:asset`. So the package declares `vite: ~8.3.5` (it was `^8.3.5`); a project declares no Vite of its own and gets the package's on its next install, any 8.3 patch and never 8.4. The patch floats: the tables ran on 8.3.5, and a project's next install may take a later 8.3 patch nobody here ran them on (a fresh npm install took 8.3.8, and everything passed). On a Vite upgrade, run `vite/build.test.ts`: the `REFUSED`, `LEAKS` and `BUILDS` tables are what says whether the boundary still holds. `postcss` is a direct dependency.
- **Export is run, not only typed.** `scripts/export.test.ts` runs a real cold `design-hub export` of the brand template's artboard in a throwaway project (`scripts/lib/export-smoke.ts`) when Chrome is found and skips, saying why, when it is not; `release-check` runs the same export itself and fails without Chrome, so a release is never cut on a machine that skipped it.
- **`pnpm quality` keeps what the tests said.** Each run writes coverage to a folder of its own (`.coverage/run-XXXXXX`, removed after), so two runs in one checkout never delete each other's, and the test step's output goes to a log there that is printed when that step fails. Eighteen runs here (twelve plain, six with every core busy) did not reproduce the one-in-ten failure, so its cause is not named; the next one prints the failing test.
- **Studio's list of slugs is a file, not the server's.** `_p/all.js`, emitted by the build, lists every slug; the gate never gives it to a Client. The server keeps no build manifest and no list of slugs. So the index read cannot be section 4's `visiblePrototypes(actor, viewAs?): string[]`, since the server cannot know an internal slug. It is `visiblePrototypes(actor, viewAs?)` returning `{ view, clientFacing }`: the view the person gets (`viewOf`, as comments use it) and every client-facing slug. Studio's view loads `_p/all.js` and then each entry; a Client's view loads only the client-facing entries. An entry that is not there (refused, or not built) is skipped; one that fails otherwise, or Studio's list failing to load, shows an error, never an empty index.
- **The registry module.** `virtual:design-hub/registry` has one interface in dev and in a build: `allSlugs()` and `entryOf(slug)`, both async, and `guideDocs`. Served it keeps a map (there is no gate in dev); built it holds no slug and asks for an entry with a `HEAD` first (`probeEntry` in `core/prototype.ts`): a 404, or a 200 that is not JavaScript (the host's page for an entry that was never built), reads as none; any other answer (401, 500, a 503 in an outage) is an error, so an outage never shows a Client "Nothing shared yet". A slug with a README and no `index.tsx` has no `load`.
- **Reserved paths.** `guide`, `api` and `assets` are never a prototype (`core/prototype.ts`): the registry's scan skips them, `design-hub new` refuses them, and the gate treats them as the hub's.
- **The store.** `hub3:audiences`, field `<slug>`, value `client`. Only client-facing is stored; setting internal deletes the field. Absent, or any other value, reads as internal. No migration: every prototype on an upgraded site is internal until Studio switches it. A switch flipped under `design-hub dev` writes the local store only; the deployed site has its own.
- **The rules.** `can` gained `audience`: Studio yes, Client no, in the row-by-row table. `setAudience(actor, prototype, audience)` checks the slug and the value and names every problem; `audienceOf(prototype)` takes no actor, for the gate. API: query `prototypes` (with `viewAs`, an unknown value 422, as `comments`) and command `prototype.audience`.
- **Comments on an internal prototype.** Section 1 measures every read and write path refusing an internal prototype to a Client, and an answer that is not empty would confirm a slug. So for a Client's view, a prototype that is not client-facing has no comments: `listComments` is empty (Studio's Client view too), `allComments` leaves it out, and every op by id and `add` answer `not_found`, the same as an unknown id, through the one helper (`seen`) and `reachable`. Writes judge the actor's own kind, not `viewAs`.
- **The gate.** After the session check and before passing, for anyone but Studio: a path under `/_p/<x>/` is 404 unless `<x>` is a client-facing slug, so `/_p/all.js` is always 404; a page path whose first segment is a slug and not reserved is 404 unless that slug is client-facing; For anyone but Studio the decoded first segment must be empty, the hub's own (`assets`, `api`, `guide`, `_gate`, `index.html`, `favicon.svg`), `_p` exactly, or a prototype slug; anything else (`_P`, `_p;x`, `_p.`, a full-width `＿p`, `/robots.txt`) gets the same 404. How Vercel's file server resolves an odd path is not known, so the gate fails closed further: a path that does not decode, keeps a `%` after decoding, holds a backslash, a `.` or `..` segment, or an empty segment other than the last, gets the same 404. An encoded space or letter passes. The 404 for an internal prototype and for one that does not exist are byte for byte the same. A Client's prototype path asks the store for that slug's audience on every request, no cache; a store that does not answer, or is not configured, is 503. Studio skips the lookup.
- **The token carries the kind.** The fresh branch asks the store nothing, so to tell Studio from a Client without a store read the session token is now `p4.<id>.<epoch>.<kind>.<expires>.<checkedAt>.<sig>`, the kind signed. A valid `p3` token is still honoured and read as stale, so its next request asks the store and re-issues it as `p4`; nobody is signed out by this release. A Client's cookie edited to say Studio fails the signature.
- **The index.** Built from the server's answer. Studio, outside Client view, sees each prototype's audience beside its row (Internal on the internal comments' amber, now one token, `--sys-internal`, that the comment layer reads too) and a switch, outside the row's link: optimistic, one save at a time per prototype (the switch waits), and a failed save puts back only that prototype, with a toast. **Client view** on the index is the comments' (`proto:client-view`), with the same note and **Leave**; in it no switch and no audience word shows, and an internal prototype's page shows "No prototype called …" with the note beside it. **Leave** stays on screen when the index fails to load. A Client with nothing shared sees "Nothing shared yet". With no review API at all (a 404, or `vite preview`'s page instead of JSON), the index shows Studio's view. The fold once called "Internal explorations" is now "Explorations", since internal means one thing.
